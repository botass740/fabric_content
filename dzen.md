## Что сделано (готово и работает)

### Генерация
- Полный пайплайн работает: матрица осей → темы → заголовки → план → статья → проверка → обложка.
- Абстракция LLM-клиента (`llm.py`) — можно переключать провайдера через `LLM_PROVIDER` (`openrouter_client.py` / `anthropic_client.py`).
- Этап проверки сюжета `story_check.py` + `story_check_prompt.txt`.
- Обложки: FLUX через OpenRouter. `flux_client.py` принимает `base_url` (был захардкожен `openrouter.ai` — исправлено, теперь тоже через прокси). Fallback на PIL-placeholder при сбое.
- Промты переписаны под качество: квоты на цифры/диалоги/бренды, запрет афоризмов, постпроцессор `_cut_second_ending()`.

### Устойчивость доставки в Telegram (сделано в этой сессии)
Проблема была в том, что статья и обложка генерировались нормально, но превью не доходило до Telegram — бесплатный прокси-воркер рвал соединение на больших загрузках. Один упавший `send` ронял всю выдачу превью, и пользователь видел ложное «Ошибка генерации».

Что добавлено в `app/telegram/bot.py`:
- Таймауты в **обеих** ветках `ApplicationBuilder` (прокси и прямая): `connect/read 30s`, `write 60s`, `pool 30s`. Дефолтные 5 секунд через прокси не выживали.
- `_retry_send(coro_factory, what=, attempts=4)` — ретраи с backoff на `NetworkError`/`TimedOut`, уважает `RetryAfter`.
- `_compress_for_preview(image_path, max_side=1280, quality=82)` — PIL, PNG 1.6 МБ → JPEG ~150–250 КБ.
- Доставка превью сделана нефатальной. Если превью не ушло, но статья создана — честное сообщение «Статья готова (ID: N), но превью не доставилось из-за сети. Открой её через /list или /queue».

**Важный нюанс про две картинки:** сжатие применяется **только к превью в Telegram**. В Дзен через `file_chooser.set_files()` уходит оригинальный файл (`dzen_publisher.py:303`) — качество обложки не страдает.

### Вход в Дзен (частично)
Профиль Chromium **нельзя** просто скопировать Windows → Linux: куки шифруются ключом ОС (DPAPI), на Linux не расшифруются. Поэтому переносим `storage_state` — кроссплатформенный JSON с куками и localStorage.

- `tools/dzen_login_local.py` — **отработал локально успешно**. Открывает существующий локальный профиль, ждёт подтверждения входа, сохраняет `dzen_state.json`.
- `dzen_state.json` **готов и лежит в корне проекта**: 81 кука (34 yandex, 36 dzen), 3 origin.
- `tools/dzen_load_state.py` — для VPS, ещё **не запускался**. Заливает куки через `add_cookies()` + localStorage через `page.evaluate` (важно: `launch_persistent_context()` не принимает `storage_state`, только `new_context` — на этом уже спотыкались).

Оба скрипта сами добавляют корень проекта в `sys.path` — запускать из корня: `python tools/dzen_login_local.py`.

## Что осталось сделать

Порядок примерно такой:

1. **Восстановить доступ к VPS** — блокер, см. ниже. Пока нет SSH, всё остальное стоит.
2. **`sudo apt install -y xclip`** — публикатор вставляет заголовок и текст через `pyperclip` + Ctrl+V, без xclip буфер обмена на Linux не работает. Ставит пользователь: sudo требует пароль.
3. **Xvfb** — публикатор запускает Chromium в headful (`headless=False`), а на VPS `DISPLAY` пустой. Xvfb и `xvfb-run` уже установлены, нужно прокинуть дисплей боту.
4. **Перенести `dzen_state.json` + оба скрипта на VPS**, запустить `xvfb-run -a python tools/dzen_load_state.py`, убедиться, что вход подхватился.
5. **Первая тестовая публикация** через бота.
6. **systemd/tmux** — чтобы бот жил после закрытия SSH, с прокинутым `DISPLAY`.

## Блокер: нет доступа к VPS

Пользователь переехал на свой VPS `171.22.180.27` (юзер `botas`). Старый (`77.222.46.139`, юзер `owner`) отключён за неоплату.

**На новый VPS не заходит ни пользователь, ни агент.** Симптом:
```
ssh botas@171.22.180.27
Connection closed by 171.22.180.27 port 22
```

### Диагностика (проведена, выводы надёжные)

Что проверено снаружи и что это значит:

- `ssh -vvv` доходит до `debug1: Connection established`, падает на `kex_exchange_identification: Connection closed by remote host`. То есть TCP-рукопожатие **проходит**, но сервер не присылает SSH-баннер.
- Порты 22, 80, 443, 2222 отвечают «открыто» — и **порты 9, 34567, 51234 тоже**. Заведомо закрытые порты открытыми быть не могут.

**Вывод: перед сервером стоит SYN-прокси / анти-DDoS фильтр провайдера.** Он сам отвечает на SYN за любой порт, но трафик до Ubuntu не доводит и через пару секунд рвёт сокет.

### Две гипотезы, которые уже опровергнуты — не тратить на них время повторно

- **«Дело в ключах»** — нет. Обрыв происходит на `kex_exchange_identification`, до любой аутентификации. Ни ключ, ни пароль до сервера не доходят, результат одинаковый.
- **«Провайдер режет пакеты, они не доходят»** (вывод предыдущего ИИ-агента по пустому `auth.log`) — неточно. Если бы пакеты резались, был бы **timeout**, а не `Connection closed`. Пустой `auth.log` объясняется тем, что соединение обрывает фильтр *перед* sshd, а не тем, что пакет не дошёл до сети сервера.

### Что делать дальше

1. Зайти через VNC/веб-консоль в панели провайдера (доступ идёт мимо сети) и проверить: `systemctl status ssh`, `ss -tlnp | grep :22`. Так станет ясно, жив ли sshd.
2. Написать в поддержку: «На IP 171.22.180.27 все TCP-порты, включая заведомо закрытые (9, 34567), отвечают на SYN, но соединение обрывается до передачи данных. В auth.log попыток подключения нет. Похоже, анти-DDoS фильтр перехватывает трафик и не проксирует на сервер. Прошу проверить фильтрацию/whitelist для порта 22.»
3. Уточнить, не требуется ли активация сервера или добавление IP в whitelist после оплаты — у провайдеров с защитой это иногда обязательный шаг.

## Известные грабли (проверено на практике)

- `launch_persistent_context()` **не принимает** `storage_state`. Только `new_context`. Для persistent-профиля — `add_cookies()` + localStorage через `evaluate`.
- Профиль Chromium не переносится между Windows и Linux (шифрование куков ключом ОС).
- Скрипты в `tools/` не видят `app/`, если не добавить корень в `sys.path` — уже добавлено в оба dzen-скрипта.
- Bash-инструмент иногда работает не из корня проекта: при `scp`/`py_compile` ставить `cd /f/Zerocoder/Dzen_2 && ...`.
- В PowerShell префикс `!` не работает — это префикс промта Claude Code, не оболочки.
- Низкая загрузка CPU/RAM на VPS (1–4%, 1.17 из 4 ГБ) — норма: бот I/O-bound, почти всё время ждёт сеть.
- Отключить FLUX временно: в `images.py:134` заменить `if settings.openrouter_api_key:` на `if False:`.
